What is the cf_clearance cookie?

Last reviewed 10 November 2026 · 5 min read

Short answer: cf_clearance is the cookie Cloudflare sets on your browser after it has decided you are not a bot. It is not a token you solve — it is a receipt issued by Cloudflare's edge, stamped with the challenge you passed, bound to your IP address and user agent, and valid for a limited time (30 minutes by default). Everything that goes wrong with it later goes wrong for one of those three reasons.

Where it comes from

The cookie appears only after one of three challenge types completes:

  • JS challenge — Cloudflare's "Checking your browser" interstitial. It runs a small JavaScript proof of work in the page, then the edge hands out clearance.
  • Managed Challenge — Cloudflare chooses between JS, a visible CAPTCHA, or nothing at all, per request. Which one ran is not visible from the client side.
  • Turnstile widget — the token your page gets from the widget is not the clearance cookie. The widget token goes to your own origin for server-side verification; cf_clearance is set separately by Cloudflare's edge on the same request flow.

That distinction matters: teams routinely pay for a Turnstile token, paste it into a header, and wonder why the page is still a challenge page. The token answers "a human solved the widget"; the cookie answers "this connection finished the challenge".

What is inside it

The value looks like an opaque string of roughly 40–60 characters plus a dotted suffix, and it is signed. Cloudflare does not publish the format, but the practical implication does not depend on the internals: you cannot mint one client-side without executing the challenge, and you cannot move one between machines without it dying.

The three cookies people confuse with it

  • __cf_bm — bot management telemetry, not clearance. It is set routinely and proves nothing.
  • cf_chl_2 / cf_chl_prog — transient state of the challenge currently running. If you see these, you have not passed yet.
  • cf_clearance — the only one that means "past the edge".

How to get one on purpose

There are three honest paths, and the third is the one people skip:

  1. Drive a real browser. Playwright or Selenium on the same machine that will use the cookie. Pass the challenge once, export the cookie jar, and keep the same IP and user agent for every request that follows. If the challenge is interactive (Turnstile), this does not work unattended.
  2. Use a solving service. For scripting workloads, an API that returns cf_clearance for a given site key and URL is the usual route; SolveHub exposes one REST endpoint for Cloudflare interstitial and Turnstile tasks and bills per completed task. Whatever service you use, check that the returned cookie is paired with the same proxy exit that will make the real requests.
  3. Do not need it. If you can hit the origin's sitemap, RSS feed, API endpoint or a partner data feed, the challenge never appears. This is the cheapest option and the least often considered.

Why reuse fails in practice

  • Cookie exported, then the request goes out through a different proxy — dead on the IP binding.
  • Cookie exported from Chrome, replayed with a Python requests header set — dead on the TLS fingerprint.
  • Cookie cached in Redis with a 24-hour TTL — dead after 30 minutes, but your code keeps sending it.
  • Cookie shared across parallel workers — the first two work, the rest look like credential stuffing.

The fix is architectural, not a better solver: pin one session to one exit IP, one fingerprint and one cookie, and refresh the whole triple when the cookie expires.

FAQ

Does cf_clearance work on a different subdomain? No. Clearance is per hostname and zone.

Can I generate it without a browser? Not by computing it. Only by completing the challenge, which needs a JS engine or a service that runs one for you.

Why do I get a 403 with a valid-looking cookie? Usually IP or user-agent drift between issuance and use. Log both on both sides before blaming the solver.
