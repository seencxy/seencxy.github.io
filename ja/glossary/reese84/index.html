reese84 クッキーとは

最終確認 2026年11月10日 · 約5分

結論から: reese84 は Imperva（旧 Incapsula）の JavaScript センサーが実行され、判定を通ったあとに発行されるクッキーです。寿命は短く、一般的に 5〜15 分。発行したセッション、User-Agent、IP に紐づきます。かつての incap_ses / visid_incap に代わって、ボット判定の本命になりました。

発行の流れ

ページはスクリプトを読み込みます。パスに UT.mvc を含むものが多いですが、サイトごとの固有 URL の場合もあります。スクリプトはブラウザの信号を集め、サイト固有の鍵で暗号化してエンドポイントに POST し、その応答としてクッキーの値が返ります。ここから 3 つの帰結があります。

  1. そのスクリプトを動かさない限り、クッキーは計算できません。鍵はサイトごとに異なり、更新されます。
  2. スクリプトの URL そのものが分からないと要求できません。URL はサイトごとに違い、チャレンジ用 HTML の中にしか出てこないこともあります。
  3. 取得後に別マシンへ移しても通りません。次のリクエストで紐づけが再検証されます。

なぜすぐ失効するのか

紐づけ先破ったときの症状
IP アドレス数秒後のリクエストでも再チャレンジになります。
User-Agent と TLS フィンガープリントクッキーは有効に見えるのに、エンドポイントは Imperva のブロックページを 403 で返します。
クッキーの寿命（分単位）動いていたのに実行の途中で落ちます。長いジョブはキャッシュではなく更新が必要です。
リクエスト頻度早期に失効します。50 回は耐えた値が、200 回目で落ちます。

周辺のクッキー

  • incap_ses_* ― セッション識別子。ゾーンごとに接尾辞が付きます。
  • visid_incap_* ― 訪問者識別子。寿命は長く、再訪者のスコアリングに使われます。
  • nlbi_* ― ロードバランサのアフィニティ用。セキュリティ用ではありませんが、セッションの安定に効きます。

現実的な扱い方

自分でセンサーを動かす。 固定 IP の実ブラウザならチャレンジを通り、短い寿命のあいだクッキーを保持できます。真っ当ですが、コストはかかります。

クッキーを要求する。 URL（サイトが隠す場合はスクリプト URL も）を渡すと、新しい reese84 と、それを使うべきプロキシ出口を返す API があります。肝心なのは、実リクエストもその出口から出ることです。出口が違えば、どれだけ新しいクッキーでも意味がありません。

そもそも避ける。 Imperva 保護のサイトでも、サイトマップ、RSS、静的ファイル、一部の JSON API は保護外のことが多いです。欲しいデータがそこから取れるなら、クッキーは不要です。

よくある質問

reese84 と incap_ses は同じものですか。 いいえ。incap_ses はセッション ID で、reese84 はセンサーが出した判定を運びます。

1 つのクッキーを並列リクエストで使い回せますか。 同じ IP とフィンガープリントなら、ごく短時間だけ可能です。急なファンアウトはそれ自体が失効の引き金になります。

JSON を期待したエンドポイントがチャレンジ HTML を返すのはなぜですか。 クッキーが切れたか、セッションが変わったかです。同じ値を再試行せず、取り直してください。
