_abck クッキーとは

最終確認 2026年11月10日 · 約5分

結論から: _abck は Akamai Bot Manager の主要クッキーです。一度取れば使える「入場券」ではなく、エッジが応答のたびに書き換える「台帳」に近いものです。ブラウザが送ったセンサーデータに対する判定が値に埋め込まれていて、同じ値を保持し続けると、その判定は古くなっていきます。

値は 3 つの区切りでできている

典型的な値は F1A2B3...~-1~YAAQ... のように、チルダで区切られた 3 つの部分から成ります。

位置中身実務での意味
1 つ目bmak（センサースクリプト）が集めたデータのハッシュスクリプトが動いたことと、その報告内容を証明します。書き換えるとクッキー全体が無効になります。
2 つ目判定フラグ0 は未判定、1 はボットと判定、~0 や -1 は通過。ヘッダーをどれだけ整えても、1 が入っていれば通れません。
3 つ目発行記録（エンコードされた時刻と参照情報）エッジがその判定の古さを測る材料です。古い値は再評価されます。

なぜ毎回書き換わるのか

Akamai は入口で一度だけ判定するのではなく、セッションを継続的に評価します。応答ごとに判定が更新されうるため、5 分前に書き出したクッキーは、すでに「疑わしいセッション」を指していることがあります。理由は、リクエスト頻度が跳ねた、IP が変わった、名乗っている User-Agent と TLS フィンガープリントが食い違った、などです。

スクレイピングで最も多い失敗はここです。_abck をログイントークンのように扱ってキャッシュし、ワーカーや IP をまたいで使い回すと、ほぼ確実に落ちます。

一緒に動かす必要があるクッキー

  • bm_sz ― セッションとテレメトリ用。_abck と必ずセットで移動させます。
  • bm_sv ― 寿命が短く、特定のエンドポイント付近で現れます。
  • ak_bmsc ― 旧世代の判定用。_abck を持たないプロパティではこちらが使われます。

_abck だけを移す、あるいは bm_sz だけを移すのは、リプレイ攻撃のシグナルになります。

通すための現実的な選択肢

  1. センサーを実際に動かす。 保護されたページを実ブラウザで開き、センサースクリプトを実行させ、以降のリクエストで同じ IP・User-Agent・TLS を保ちます。確実ですが、セッションごとにブラウザを 1 つ消費します。
  2. センサーデータを生成する。 生成スクリプトは難読化され、頻繁に変わります。自前で追随するのは終わりのない作業なので、URL を渡すと有効な _abck を返す API に置き換えるのが一般的です。この用途向けの API は、完了したタスクだけを課金する従量制が主流です。
  3. そもそも避ける。 目的のページすべてが保護されているとは限りません。JSON エンドポイント、サイトマップ、モバイル向け API は保護外のことが多く、こちらのほうが安く済みます。

よくある質問

_abck はデコードできますか。 3 つ目の時刻は読めますが、1 つ目はセンサー入力のハッシュです。デコードしても、有効な値を作り直すことはできません。

新しい _abck なのに 403 が返るのはなぜですか。 2 つ目のフラグが 1 になっていることが多いです。エッジはすでにそのセッションをボットと判定しており、クッキーは許可証ではなく判定結果を運んでいます。

リクエストごとに取り直す必要がありますか。 いいえ。セッションごとに 1 つで、サイトが定める周期で更新します。リクエストごとに回すこと自体がシグナルになります。
