What is the _abck cookie?

Last reviewed 10 November 2026 · 5 min read

Short answer: _abck is the main cookie of Akamai Bot Manager. It is not a ticket you earn once — it is a ledger the edge keeps rewriting. Every response can hand you a new value, and the value encodes a verdict about the sensor data your browser sent. If you capture an _abck and hold it still, it starts decaying immediately.

The three segments

A typical value looks like F1A2B3...~-1~YAAQ... — three parts separated by tildes:

PositionWhat it holdsWhat it means in practice
1stA long hash of sensor data collected by bmak / the sensor scriptProves that a script ran and what it reported. Editing it invalidates the whole cookie.
2ndThe verdict flag0 = unknown yet, 1 = seen as bot, ~0 or -1 = accepted. A 1 is the one that blocks you no matter how good your headers look.
3rdIssuance record (encoded timestamp and reference data)Lets the edge judge how old the verdict is. Stale values get re-evaluated.

Why it changes on every response

Akamai evaluates sessions continuously rather than once at a gate. Each response can revise the verdict, so the cookie you exported five minutes ago may already describe a session the edge now considers suspicious — for example because your request rate jumped, your IP changed, or your TLS fingerprint stopped agreeing with the user agent you claim.

This is the single most common failure in Akamai scraping: developers treat _abck like a login token, cache it, and reuse it across workers and IPs. It is closer to a browser session's heartbeat.

The other Akamai cookies

  • bm_sz — session/telemetry cookie, paired with _abck; must move with it.
  • bm_sv — short-lived, appears around sensitive endpoints.
  • ak_bmsc — older bot manager cookie, still present on some properties.

Moving _abck without bm_sz, or the reverse, is a reliable way to look like a replay attack.

Getting past it

There are two real options and one that does not exist:

  1. Run the sensor. Load the protected page in a real browser, let the sensor script execute, and keep the whole jar plus the same IP, user agent and TLS stack for subsequent requests. Works, but costs a browser per session.
  2. Generate sensor data deliberately. The script that produces it is obfuscated and changes; maintaining your own generator is a treadmill. A solving API that returns a valid _abck for a given URL is the usual substitute — SolveHub handles Akamai tasks this way and bills per completed task.
  3. Do not clear it. Not every Akamai-protected site needs bot clearance for the pages you actually want: JSON endpoints, sitemaps and mobile APIs are often unprotected and far cheaper to read.

FAQ

Can I decode _abck? You can decode the third segment's timestamp, but the first is a hash of sensor input. Decoding does not let you forge a valid one.

Why does a fresh _abck still get a 403? Often because the flag in segment two is 1 — the edge already decided the session is a bot, and the cookie is reporting that decision rather than granting access.

Do I need a new one per request? No. One per session, refreshed on the schedule the site enforces. Rotating it per request is itself a signal.
