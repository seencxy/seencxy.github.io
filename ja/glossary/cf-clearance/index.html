cf_clearance クッキーとは

最終確認 2026年11月10日 · 約5分

結論から: cf_clearance は Cloudflare が「ボットではない」と判断したブラウザに付けるクッキーです。こちらが解いて送るトークンではなく、Cloudflare のエッジが発行する「領収書」です。通過したチャレンジの種類が刻まれ、IP アドレスと User-Agent に紐づき、有効期間は既定で 30 分です。その後に起きるトラブルは、ほぼこの 3 つのどれかが原因です。

どこから来るのか

このクッキーは、次の 3 種類のチャレンジのいずれかを通過した後にだけ現れます。

  • JS チャレンジ ― 「ブラウザを確認しています」の画面。ページ内で小さな JavaScript の計算を走らせ、成功するとエッジがクリアランスを渡します。
  • Managed Challenge ― JS を出すか、目に見える CAPTCHA を出すか、何もしないかを Cloudflare がリクエストごとに選びます。どれが動いたかはクライアント側からは分かりません。
  • Turnstile ウィジェット ― ここが最も誤解される点です。ウィジェットが返すトークンはクリアランスクッキーではありません。ウィジェットのトークンは自サーバーでの検証に使うもので、cf_clearance は同じリクエストの流れの中で Cloudflare のエッジが別に発行します。

この区別は重要です。Turnstile のトークンを買ってヘッダーに貼り、それでもチャレンジ画面が出ると不思議に思う、という話がよくあります。トークンが答えるのは「人間がウィジェットを解いた」であり、クッキーが答えるのは「この接続はチャレンジを完了した」です。

中身と、何に縛られているか

値は 40〜60 文字程度の不透明な文字列と、ドットで区切られた接尾辞からなり、署名されています。Cloudflare は形式を公開していませんが、実務上の結論は中身に依存しません。チャレンジを実行せずにクライアント側で作ることはできず、別のマシンへ移すと死にます。

縛られている対象変わるとどうなるか
IP アドレスクリアランスは即座に無効になり、再びチャレンジになります。プロキシを回すと余計に弾かれるのはこのためです。
User-Agent / TLS フィンガープリント同じ結果です。ブラウザが受けたクッキーを requests から再生すると、フィンガープリントだけで落ちます。
ゾーンあるサイトのクッキーが別のサイトで効くことはありません。同じ Cloudflare アカウントの下でも同じです。
時間既定の寿命は 30 分。セッション限りのクッキーはブラウザを閉じると消えます。古いクッキーは無いより悪い状態です。再生のシグナルになるからです。

混同されやすい 3 つのクッキー

  • __cf_bm ― Bot Management のテレメトリで、クリアランスではありません。日常的に付与され、通過を意味しません。
  • cf_chl_2 / cf_chl_prog ― 実行中のチャレンジの途中状態です。これが見えているなら、まだ通過していません。
  • cf_clearance ― 「エッジを通り抜けた」を意味する唯一のクッキーです。

意図的に手に入れる 3 つの方法

  1. 実ブラウザを動かす。 そのクッキーを使うのと同じマシンで Playwright や Selenium を動かします。一度チャレンジを通し、クッキージャーを書き出し、以降のリクエストで同じ IP と User-Agent を保ちます。インタラクティブなチャレンジ（Turnstile）だと無人では通りません。
  2. 解決サービスを使う。 スクリプト処理では、サイトキーと URL を渡すと cf_clearance を返す API を使うのが一般的です。SolveHub は Cloudflare のインタースティシャルと Turnstile を1 つの REST エンドポイントで扱い、完了したタスクだけを課金します。どのサービスを使う場合でも、返ってきたクッキーと、実際にリクエストを出すプロキシの出口が同じであることを確認してください。
  3. そもそもクッキーを必要としない。 オリジンのサイトマップ、RSS、API エンドポイント、提携先のデータフィードに届くなら、チャレンジは現れません。最も安く、最も見落とされる選択肢です。

使い回しが失敗する典型

  • クッキーを書き出したあと、別のプロキシからリクエストを出した ― IP の縛りで落ちます。
  • Chrome から書き出したクッキーを Python の requests のヘッダーで再生した ― TLS フィンガープリントで落ちます。
  • Redis に 24 時間の TTL でキャッシュした ― 30 分で無効になるのに、コードは送り続けます。
  • 並列ワーカー間でクッキーを共有した ― 最初の 2 本は通り、残りはクレデンシャルスタッフィングのように見えます。

必要なのは優れたソルバーではなく、設計の変更です。1 つのセッションを 1 つの出口 IP、1 つのフィンガープリント、1 つのクッキーに固定し、クッキーが切れたら 3 つまとめて入れ替えます。

よくある質問

別のサブドメインでも cf_clearance は効きますか。 効きません。クリアランスはホスト名とゾーン単位です。

ブラウザなしで生成できますか。 計算では作れません。チャレンジの完了が必要で、そのためには JS エンジンか、代わりに実行してくれるサービスが要ります。

有効に見えるクッキーなのに 403 が返るのはなぜですか。 発行時と使用時で IP か User-Agent がずれていることがほとんどです。ソルバーを疑う前に、両側で両方をログに残してください。
