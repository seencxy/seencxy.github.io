_px3 クッキーとは

最終確認 2026年11月10日 · 約5分

結論から: _px3 は PerimeterX（現 HUMAN Security）のセンサー判定を通ったブラウザに発行されるクッキーです。サイトが持つ鍵で暗号化されたペイロード、ペイロード内に埋め込まれた短い寿命、そして HMAC 署名の 3 つでできています。セッショントークンのように別のクライアントへコピーして使えるものではありません。署名はペイロード全体を覆っており、サーバーは独自の周期で再署名します。

中身は 4 つの区切りでできている

_px3 の値はコロンで区切られた 4 つの部分からなります。暗号化ペイロード、時刻、ハッシュ、署名です。実務で重要なのは次の点です。

部分何を決めているか
暗号化ペイロードPerimeterX がそのセッションに対して算出したスコア、発行時の IP と User-Agent、そして _pxvid と結びつく UUID が入っています。
時刻発行時刻。どれだけの期間を「新しい」とみなすかはサイトのポリシーが決めます。
署名サイト固有の鍵による HMAC。ペイロードを 1 バイトでも変えると壊れるので、低いスコアを高いスコアに書き換えることはできません。

2 つの失効時間がある

ここで多くの実装が壊れます。サーバーがクッキーに付ける Expires と、ペイロードに埋め込まれサーバーが独自に適用する寿命は別物で、両者が一致する必要はありません。Expires が 2 時間先でも、ペイロードの寿命は発行時点から測られているため、返ってきた瞬間にすでに期限が近いことがあります。

ブラウザが捨てるまでクッキーを使い回すと、ジャーの中ではまだ有効に見えるクッキーで、最後のほうはチャレンジ応答ばかり返ってきます。対策は Expires 属性を読むことではなく、応答ごとに Set-Cookie ヘッダーを見てジャーの該当エントリを無条件に差し替えることです。

別のマシンへ移すと通らない理由

  • ペイロードには発行時の IP と User-Agent が記録されています。別ホストへ移したジャーは、たいてい新しいチャレンジを受けます。
  • _pxvid と _pxhd が一緒に移動します。_pxvid を欠いた _px3 は、エッジが照合できないセッションに対する署名でしかありません。
  • ペイロードのスコアは「確認される」だけでなく「再評価される」ことがあります。以前はクリーンだったセッションでも、機械的な速度でリクエストを送り始めると、次の再署名でスコアが下がります。

s2s という別の経路

PerimeterX には、一部の連携で使われるサーバー間（s2s）のトークン方式があります。この経路では HUMAN の API で直接検証するトークンが返り、ブラウザ側のクッキーを必要としません。検証許可を得ているサイトがこの方式に対応しているなら、クッキージャーを維持するよりはるかに安定します。PerimeterX のドキュメント に、両方のモードを API からどう扱うかをまとめています。

s2s が提供されていない場合の現実的な選択肢は 2 つです。実ブラウザでセンサーを動かし、ジャーとネットワーク上の同一性を丸ごと保つか、対象 URL に対する有効な _px3 を解決 API から受け取るかです。ペイロードを自分で再生成するのは、難読化された頻繁に変わるスクリプトとサイトの鍵を再実装することになり、維持コストに見合いません。

関連するクッキー

  • _pxhd ― HTTP-only で _pxvid に紐づきます。多くのサイトで _px3 とセットで必要です。
  • pxcts ― 短命のチャレンジトークン。常に更新されます。
  • _pxde ― センサー実行中に置かれる遅延クッキーのプレースホルダーです。

よくある質問

_px3 のペイロードは復号できますか。 実用にはなりません。サイトが管理する鍵で暗号化されているため、長さは分かっても中身は分かりません。クライアント側に鍵はありません。

失効前に _px3 が効かなくなるのはなぜですか。 サーバーが発行時点から独自の寿命を適用しており、それがクッキーの Expires より短いことがあるためです。Set-Cookie が返るたびにジャーのエントリを差し替えてください。

別の IP からでも _px3 は通りますか。 長くは通りません。ペイロードには発行セッションの IP と User-Agent が記録されており、機械的な速度で評価されたセッションは次の再署名でスコアを下げられます。
